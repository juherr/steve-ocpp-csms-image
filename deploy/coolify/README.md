# Running the image on Coolify

[`steve.yaml`](steve.yaml) is a [Coolify](https://coolify.io) service template:
SteVe and a MariaDB, every credential generated by Coolify, the public URL
routed by Coolify's proxy. Paste it once and Coolify deploys a working
instance; paste it again and you get a second one, with its own network,
volume, database and credentials — but the same proxy and image tags as the
first, which is not multi-tenant isolation (see *Several instances*).

It is plain Docker Compose with Coolify's conventions on top — the header
comments, the `SERVICE_*` variables — so it is also the file to submit to
Coolify's catalog when that becomes possible (see *Catalog*). CI runs it as
it is, with plain Compose standing in for Coolify; see *What is tested*.

## Install

1. In Coolify: **+ New → Docker Compose Empty**, choose the server and the
   destination.
2. Paste the whole of [`steve.yaml`](steve.yaml) into **Docker Compose file**
   and **Save**. Coolify parses it, shows the two services, `steve` and
   `steve-db`, and generates the variables below.
3. Give the `steve` service a domain, if Coolify did not generate one, and
   check the variables (see *Generated credentials*).
4. **Deploy**. The first boot migrates the empty database before SteVe starts:
   the `steve` container becomes healthy within the 150 s the healthcheck
   allows, under a minute on a native host (measured).

The image is the one line that names a release: the `image:` of the `steve`
service, `ghcr.io/juherr/steve:steve-X.Y.Z`. It is a tag without a digest on
purpose: a JRE update republishes the same tag (see
[*Tags*](../../README.md#tags)), and the template is meant to take it on the
next pull of the image rather than through a change to the file — see
*Updating* for the action that pulls. Pin it by digest yourself if you would
rather review that change: append the index digest `docker buildx imagetools
inspect` prints, `…:steve-X.Y.Z@sha256:<digest>`.

## Generated credentials

| Variable | Generated as | Reaches |
| --- | --- | --- |
| `SERVICE_USER_ADMIN` | 16 random characters | `AUTH_USER` — the SteVe administrator |
| `SERVICE_PASSWORD_ADMIN` | 32 random characters | `AUTH_PASSWORD` — the administrator's password |
| `SERVICE_PASSWORD_MARIADB` | 32 random characters | `DB_PASSWORD` in `steve`, `MARIADB_PASSWORD` in `steve-db` — one value, shared |
| `SERVICE_PASSWORD_ROOT` | 32 random characters | `MARIADB_ROOT_PASSWORD` — not used by SteVe |
| `SERVICE_URL_STEVE_8180` | the domain | Coolify's proxy, which routes it to the container's `8180` |
| `STEVE_MEMORY_LIMIT` | default `1g` | `mem_limit` of `steve` — see *Memory* |

Nothing else is a credential: no upstream default reaches the container. The
compiled-in `admin`/`1234` is replaced; the Web API is off; unknown charge
points are rejected — see *Security*.

**These values are read once.** SteVe creates its administrator from
`AUTH_USER` and `AUTH_PASSWORD` on its first start, when the database holds no
administrator yet, and never again: changing `SERVICE_PASSWORD_ADMIN` after
the first deploy leaves the old password the one that works (measured on
`steve-3.14.1`). MariaDB does the same with `MARIADB_*` — they are applied to
an empty data directory only.

SteVe at that release has no page to change a password, so the way to a new
administrator password is to let SteVe create the administrator again: change
the variable in Coolify, delete the administrator's row from `steve-db`,
then restart `steve` — it finds no administrator and creates one from the
current `AUTH_USER`, `AUTH_PASSWORD` and `WEBAPI_VALUE` (measured; nothing
else in the schema references that table):

```bash
MYSQL_PWD="$MARIADB_PASSWORD" mariadb -u steve stevedb -e "DELETE FROM web_user WHERE username = '<AUTH_USER>'"
```

For the database password, `ALTER USER` in the database first, then the
variable, so that the two agree.

## Management UI and OCPP endpoints

The template serves SteVe at the root of the domain Coolify routes to it
(`CONTEXT_PATH=` empty), not under the `/steve` prefix the image uses by
default: an instance owns its domain, and the prefix would only lengthen
every URL a charge point is configured with. So:

- the management UI is `https://<domain>/manager` — `https://<domain>/`
  redirects there;
- a charge point connects to
  `wss://<domain>/websocket/CentralSystemService/<chargeBoxId>`,
  `<chargeBoxId>` being the identity registered for it in SteVe first — a
  registered one gets its upgrade (101), an unknown one a 404 (measured);
- OCPP-S (SOAP) stations use `https://<domain>/services/CentralSystemServiceOCPP16`
  (or `…OCPP15`). The WSDL SteVe serves names the request's host but
  `http://` behind the proxy (measured), so configure the station with the
  `https://` URL rather than the one the WSDL advertises.

TLS is terminated by Coolify's proxy, which forwards the WebSocket upgrade to
the container's `8180`; SteVe itself speaks plain HTTP. For charge points
using OCPP security profile 2 — Basic authentication, which requires TLS —
SteVe has to know the connection was TLS before the proxy: the template sets
`STEVE_OCPP_SECURITY_PROTOCOL_HEADER_FROM_PROXY=X-Forwarded-Proto` for that.
On a real Coolify, profile 2 over `wss://` is accepted (101) and a plain
`ws://` is redirected to `https://` by the proxy; an `X-Forwarded-Proto: http`
forged by the client does not reach SteVe — the proxy sets the header itself
(measured, Coolify 4.4.6 behind Cloudflare).

**Keep the connection alive from the charge point.** A proxy in front of
Coolify may close an idle WebSocket: behind Cloudflare the session was cut
before 150 s without traffic, and SteVe sent no WebSocket ping in that time
(measured). Set the station's `WebSocketPingInterval` below the proxy's idle
timeout — 60 s or less behind Cloudflare, with which a Heartbeat 160 s after
the BootNotification was still answered (measured). Stations that do not
implement it need a Heartbeat interval below that timeout instead.

## Security

The management UI, the OCPP WebSocket endpoint and SteVe's SOAP endpoint
(`/services/`) share the container's single port, and so the one domain.
What protects each:

- **The management UI** — SteVe's sign-in, with the generated administrator.
  It is reachable from wherever the domain is.
- **The OCPP endpoint** — the charge point's identity, which must be
  registered (`AUTO_REGISTER_UNKNOWN_STATIONS=false`), and, for profile 2,
  its Basic credentials. A charge point cannot pass an interactive login, so
  nothing stronger can be put in front of it.
- **The SOAP endpoint** — nothing: SteVe serves `/services/` without
  authentication (it answers 200 here, measured), as OCPP-S stations expect,
  and the template cannot turn it off. **Whether or not you have SOAP
  stations, `/services/` is the one path no credential protects**: keep it
  behind the access policy below, and if SOAP stations must reach it, reach
  it only from where they are.
- **The Web API** (`/api/`) — off. Upstream enables it per user, with an
  API password the administrator receives from `WEBAPI_VALUE` on the first
  start; the template pins it empty, so the administrator has none and every
  call answers 401, even with the UI password (measured). To use it, edit
  that line of the Compose file in Coolify — `WEBAPI_VALUE=${SERVICE_PASSWORD_WEBAPI}`
  has Coolify generate the secret — before the first deploy, or afterwards
  followed by the administrator reset under *Generated credentials*.

So a public domain exposes a sign-in page, an endpoint authenticated per
charge point, and one not authenticated at all. To keep the UI and the SOAP
endpoint off the internet, put an access policy in front of the domain — an IP
allow-list, a VPN-only domain, an authenticating proxy — and **exempt the
path `/websocket/CentralSystemService/`, trailing slash included**: a
policy that stops at the WebSocket path without it, or a Basic-auth
middleware over the whole domain, takes the charge points' own
`Authorization` header and locks them out. The template ships no such policy:
it would be Traefik labels whose behaviour under Coolify has not been
measured here, and the right one depends on where your charge points connect
from.

**A policy enforced in front of Coolify holds only if Coolify cannot be
reached around it.** With a CDN or an identity-aware proxy ahead of the
server, a client that connects to the server's own address with the right
`Host` header meets Coolify's proxy directly, and no policy at all. Close
that path: accept 80/443 on the server only from the front proxy's address
ranges, or reach Coolify through a tunnel and publish nothing. That closes
the outside; it does not close the path from a container on the server to
another instance, through the same proxy (see *Several instances*).

The exemption opens that prefix and nothing behind it. Encoded traversal sent
through it at the UI or the SOAP endpoint — `..;`, `%2F`, `%2f`, `%2e%2e`,
`%5C`, `//`, `;jsessionid` — never reached them: SteVe's Jetty rejects an
ambiguous path with a 400 (`Ambiguous URI path parameter`), and what it did
not reject the proxy had normalised before the access policy applied, which
then sent it to sign-in (measured, an identity-aware policy on Coolify 4.4.6
behind Cloudflare; the image's prefix at the time, the same Jetty).

## Memory

The JVM sizes its heap from the container's memory limit — and without a
limit, from the whole server, once per SteVe on it. The template sets
`mem_limit` from `STEVE_MEMORY_LIMIT`, `1g` by default: an observed working
value, not a sizing recommendation. What the heap takes of it, what the
container was measured at under `1g` and under less, and why the limit has to
hold more than the heap, are in the main README's *Memory* paragraph, under
[*Deploying on a NAS or a small board*](../../README.md#deploying-on-a-nas-or-a-small-board).
Raise it with the number of charge points; `docker stats` on the server reads
what they add. MariaDB has no limit and sizes itself.

## Backup and restore

All state is the MariaDB data directory, in the `steve-mariadb-data` volume,
named `<resource-uuid>_steve-mariadb-data` on the server (measured). A copy
of a running data directory is not a consistent backup; a logical dump is.

**A backup lives off the server.** Coolify's **Stop**, **Restart** and
**Deploy** remove both containers and create new ones — a `destroy` event
for each on every path (measured, Coolify 4.5.3) — so a file written inside
`steve-db`, its `/tmp` included, is gone after the first of them, and one on
the disk holding the volume goes with the server.

**Coolify's own scheduled backups first.** Coolify recognises a MariaDB image
inside a Service as a database component and offers it the scheduled,
engine-aware backups of its standalone databases, uploaded to S3-compatible
storage if you configure one; for MariaDB it reads `MARIADB_ROOT_PASSWORD`
and `MARIADB_DATABASE` from the container, which the template sets
([Coolify: Back up a database inside a service](https://coolify.io/docs/databases/backups)).
Run on this template, set in the UI with an S3-compatible target: the
scheduled backup succeeded, the uploaded object's checksum equal to the local copy, and
it restored into a second instance — 31 tables, schema `v1.1.6`, data and
sign-in back (measured, Coolify 4.5.3). It is set per instance: a new
instance has no schedule until someone sets one, and Coolify's API answers
`Database not found` for that database's backups, so check each instance in
the UI. **Back up now** was not run.

**A dump by hand**, the way to a file you hold yourself, and the one to take
just before an update. It has to land outside the container. On the server,
over SSH, with the container names `docker ps` shows for `steve-db` and
`steve` (Coolify suffixes them with the resource's id):

```bash
docker exec <steve-db container> sh -c 'MYSQL_PWD="$MARIADB_PASSWORD" mariadb-dump --single-transaction --routines --events -u steve stevedb' > steve-backup.sql
```

The single quotes keep `$MARIADB_PASSWORD` for the container's shell: the
password is read there and never appears on a command line. No `-t`, so
nothing but the dump reaches the file. The file is on the server's disk:
copy it off before any Coolify action. The shape of a dump that cannot pass
for a good one when it failed — a `.partial` file renamed on success, the
`-- Dump completed` last line — is in the main README's
[*Upgrading*](../../README.md#1-back-up-the-database). For a recurring copy,
use the scheduled backup above: a **Scheduled Task** on `steve-db` writes
inside the container.

To restore, stop `steve` alone, so that nothing writes while the schema is
replaced — with `docker stop`, not Coolify's **Stop** or **Restart**, which
take `steve-db` down with it. A container stopped that way stays stopped:
`unless-stopped` does not start it again (measured, plain Compose). Then:

```bash
docker stop <steve container>
docker exec <steve-db container> sh -c 'MYSQL_PWD="$MARIADB_PASSWORD" mariadb -u steve -e "DROP DATABASE stevedb; CREATE DATABASE stevedb"'
docker exec -i <steve-db container> sh -c 'MYSQL_PWD="$MARIADB_PASSWORD" mariadb -u steve stevedb' < steve-backup.sql
docker start <steve container>
```

Flyway finds the schema the dump carried and applies whatever the image has
beyond it. The drop is not optional — a dump only drops the tables it
contains, so tables a later migration added would survive into the restored
schema. CI runs these commands — the part in quotes, unchanged — with
`docker compose exec -T` against plain Compose, the dump kept outside the
container (see *What is tested*); the `docker exec` around them is not run
on a Coolify server.

**From a scheduled backup**, fetch the object Coolify uploaded — a `.dmp` —
from the S3-compatible storage with the client of your choice, and copy it
to the server. It is plain SQL, without `CREATE DATABASE` or `USE`
(measured), so it goes into the database the command names, after the same
drop and create: the same four commands, with that file in place of
`steve-backup.sql`.

**A restore brings the dump's administrator back.** `web_user` is in the
dump, so after an administrator reset, or with a dump of another instance,
the password Coolify shows for this one no longer signs in and the dump's
does (measured, Coolify 4.5.3, one instance's dump restored into another;
and in CI). The wrong dump hands over another instance's administrator.
Reset it afterwards if needed (see *Generated credentials*).

## Updating

An instance keeps the Compose file it was created from: a later change to
this template — a new tag, a variable, a fix — reaches an existing instance
only when you carry it into that instance's Compose file yourself (Coolify's
*Update a service*, linked below, says the same of its own catalog).

Change the tag on the `image:` line and redeploy. The new image brings its
Flyway migrations and applies the ones the database has not seen before SteVe
starts; a redeploy of the same tag is a no-op for Flyway. Take a backup
first, and have it off the server before you redeploy — a scheduled backup
in the S3-compatible storage, or a dump by hand copied off (see *Backup and
restore*): the redeploy destroys both containers, and a dump left inside
`steve-db` with them. **Migrations only go forward**, and putting the
previous tag back on a migrated schema is not a supported path — the way
back is that backup. The main
README's [*Upgrading*](../../README.md#upgrading) and
[*Downgrading*](../../README.md#downgrading) hold the details.

**A republished tag** — the same `steve-X.Y.Z` with a new JRE — needs the
image pulled again, which is not what a restart does. Coolify's **Advanced →
Pull Latest Images & Restart** runs a Compose pull of the tags the Service
holds and recreates the stack
([Coolify: Update a service](https://coolify.io/docs/services/operations/update-service));
whether a plain **Deploy** pulls too is on the checklist. That is the trade a
tag without a digest makes: the instance follows republications of its tag
when you pull, without a change to the file — and without one to review. With
a digest on the `image:` line it changes only when you edit that line.

Two SteVe containers must never run against one database: the charge points'
WebSocket sessions live in one SteVe process, and a migration run by a new
container while the old one still serves changes the schema under it. Do not
scale the `steve` service — Coolify refuses more than one replica in a
template anyway — and treat an update as a short outage, not a rolling one.
Whether Coolify stops the old container before it starts the new one on a
redeploy is on the checklist below.

## Several instances

Each deployment of the template is its own resource: Coolify gives it its own
network, its own volume, its own container names and its own generated
values. Two instances on one server keep their network, volume, database
and credentials apart: from one, the other's database was unreachable by
name and by address, and a charge point added to one was unknown to the
other (measured, Coolify 4.5.3); CI runs two side by side and checks that
one's administrator and data never reach the other.

They are not isolated from each other, and the template cannot make them so:

- **The proxy is shared.** Coolify's proxy joins every service's network
  (read, Coolify 4.5.3's code), so a container on the server — another
  instance, another application, either compromised — reaches any
  instance's routes through it, with that instance's `Host` header, and an
  access policy enforced in front of
  Coolify does not apply on that path. From a container on the server,
  another instance's sign-in page and `/services/` answered 200 (measured,
  Coolify 4.5.3, GET requests only; what a forged SOAP call does to a
  neighbour was not measured). Between neighbours, SteVe's own
  authentication is the boundary, and `/services/` has none.
- **Image tags are per server.** A **Deploy** or a pull for one instance
  moves the server's copy of its tag, and a restart takes the copy the
  server holds (measured, Coolify 4.5.3), so every other instance on that
  tag runs the new image at its next restart (inferred, not measured on a
  second instance). A digest on an instance's `image:` line (see *Install*)
  keeps it apart. The template pins MariaDB to a patch release so that each
  move of the engine comes as a pull request this repository's CI boots,
  not with whichever instance pulls first.

So do not sell instances on one server as isolated tenants. If a client can
run code on the server — its own application, a container — give each trust
perimeter its own server; no remedy within one server has been measured.

Create the second one **from the template, as a new resource** — not with
**Clone**. Cloning copies the environment variables, the generated passwords
included, so the clone starts with the same administrator and database
password as the original. If you do clone, regenerate the `SERVICE_PASSWORD_*`
and `SERVICE_USER_*` values *before* its first deploy: once it has started,
they no longer change anything (see *Generated credentials*).

## What is tested

[`hack/coolify-template-test.sh`](../../hack/coolify-template-test.sh) runs on
every pull request that touches this directory, against the image the
template names. Plain Compose stands in for Coolify: the script generates a
value for each `SERVICE_*` variable the template references, the way Coolify
does, and gives each installation its own project name. It checks the file —
the catalog header, the variable families, every credential generated, no
port, container name, project name, network or bind mount — then brings up
two installations side by side and checks, in each: the migration of the empty
database, no host port bound, the generated administrator signing in where
`admin`/`1234` and the other installation's administrator do not, the Web API
refused, a registered charge point's WebSocket upgrade accepted and an
unknown one's refused — all at the root paths. Then it restarts one, keeping its
volume, and checks that the schema is up to date, that a row written before
is still there and that it never reached the other one.

What plain Compose cannot stand in for — Coolify's parser, its proxy, TLS,
WebSockets through it, Clone — is the checklist below, run by hand on a real
Coolify.

## Validation on a real Coolify

Record the Coolify version, then:

- [x] The template parses: both services shown, the variables of *Generated
      credentials* generated.
- [ ] The UI answers on `https://<domain>/manager` and the generated
      administrator signs in; `admin`/`1234` does not.
- [ ] A simulated charge point — for instance
      [`ghcr.io/shiv3/ocpp-cp-simulator`](https://github.com/shiv3/ocpp-cp-simulator)
      — registered in SteVe, connects over
      `wss://<domain>/websocket/CentralSystemService/<id>` and its
      BootNotification and Heartbeat show in SteVe.
- [x] The same charge point in security profile 2 (Basic credentials over
      `wss://`) is accepted — the proof that
      `STEVE_OCPP_SECURITY_PROTOCOL_HEADER_FROM_PROXY` reaches SteVe under
      that name.
- [ ] The access policy chosen for the UI, exempting
      `/websocket/CentralSystemService/`, stops an outside browser on
      `/manager/` and `/services/` and lets the charge point through.
- [ ] The policy cannot be gone around: a request to the server's own
      address with the instance's `Host` header gets no answer, or not
      SteVe's.
- [ ] A second instance, created from the template, runs next to the first:
      different volume, network and credentials; a charge point added to one
      is absent from the other; deleting one leaves the other running.
- [ ] Clone: whether the clone's generated values equal the original's.
- [ ] Coolify's scheduled backup of `steve-db`: offered, **Back up now**
      succeeds, and the file restores — into a throwaway instance — with the
      data back after sign-in.
- [ ] The dump by hand: taken, restored into the instance, the data back
      after sign-in.
- [x] `STEVE_MEMORY_LIMIT` is honoured: `docker inspect` of the `steve`
      container shows the limit.
- [ ] A redeploy on a new tag: whether the old `steve` container is stopped
      before the new one starts, and the `Migrating schema` lines in the new
      one's log.
- [ ] The same tag again: whether a plain **Deploy** pulls the image or
      reuses the one on the server, and that **Pull Latest Images & Restart**
      does pull (the image id of the new `steve` container).
- [ ] The administrator reset under *Generated credentials*: a new
      `SERVICE_PASSWORD_ADMIN`, the row deleted, `steve` restarted, the new
      password signs in.

## Catalog

The header comments are the metadata Coolify's catalog reads — `documentation`,
`slogan`, `category`, `tags`, `logo`, `port` — so the file can be proposed to
[coollabsio/coolify](https://github.com/coollabsio/coolify) under
`templates/compose/` as it is. Not now:

- External template contributions are paused, with no date to resume
  ([contribution guide](https://coolify.io/docs/contribute/service), checked
  2026-10-31).
- The guide requires the service's repository to have at least 1,000 GitHub
  stars. That is the upstream application, SteVe
  ([steve-community/steve](https://github.com/steve-community/steve), over
  1,100), not this image's repository.
- A submission also needs a documentation page in
  [coollabsio/coolify-docs](https://github.com/coollabsio/coolify-docs). The
  header's `# minversion: 4.4.6` is the version the checklist above was run
  on, not a measured lower bound.
- The logo the header names, `svgs/steve.svg`, is a file of the catalog's
  repository, added with the submission: it is [`steve.svg`](steve.svg) here,
  the SteVe mark. Upstream ships its logo as PNGs in the web application and
  as a vector PDF,
  [`website/logo/managed-by-steve.pdf`](https://github.com/steve-community/steve/blob/master/website/logo/managed-by-steve.pdf);
  the SVG is that PDF's own paths — `pdftocairo -svg`, then the three paths of
  the mark kept, unchanged, under a square `viewBox` — not a tracing of a
  PNG. Upstream states no separate licence for its logo, so the repository's
  is assumed to cover it: the file stays under SteVe's GPL-3.0-or-later, the
  one file of this repository that is not Apache-2.0 (see `NOTICE`).
